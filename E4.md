# Experiment E4: workload and backend generality

E4 evaluates Claim (C4) and reproduces the paper's workload-generality and
backend-generality tables. The paper-facing CSVs are kept separate from fresh
server outputs: `result/e4/table6.csv` and `result/e4/table7.csv` are the
submitted targets; new runs are written below `result/e4/generated/`.

## Preparation

### Table 6: workload generality

The runner is
[`script/e4/workload_generality/measure_workload_generality.py`](script/e4/workload_generality/measure_workload_generality.py),
and the executable model suite is
[`script/e4/workload/table4_pytorch/models.py`](script/e4/workload/table4_pytorch/models.py).
It evaluates three dependency-free PyTorch workloads at 16 logical ranks:

| Workload | Input mutation | Changed partitions |
| --- | --- | --- |
| ResNet | `torch.compile` with the eager backend | compute, matmul, memory |
| BERT | FSDP sharding | communication, sync |
| ViT | activation checkpointing | compute, matmul, memory |

The changed partitions are also checked offline from the executable workload
source rather than trusted as case labels.  The analyzer compares the workload's
parsed anchor/candidate options, resolves them to framework API sites in the
Python AST, and maps those API semantics to code partitions.  This check reuses
`result.json`; it does not recapture traces or alter the reported timing samples.

The anchor and candidate use the same BF16 `table4-lite` workload preset. The
candidate trace is built once, then the runner measures full replay against
plan/filter/selective replay. It reports the initialization metric, core
refresh speedup, and compact-trace reuse rate. Capture and JSONL parsing are
outside the core-refresh timing boundary.

### Table 7: backend generality

The backend runner is
[`script/e4/backend/run_backend_generality.sh`](script/e4/backend/run_backend_generality.sh).
It builds the pinned ASTRA-Sim/ns-3 backend with the RAS overlay, regenerates
the candidate Chakra ET workload, applies one operation-duration mutation per
case, and compares full simulation with RAS refresh on the same candidate ET
prefix.

The six cases are:

| Workload | Mutations |
| --- | --- |
| GPT-3 2.7B, 16 modeled ranks (TP1-PP8-DP2, GBS 512) | attention backward, MLP backward, optimizer step |
| Routed-MoE, 16 modeled ranks | attention backward, router backward, optimizer step |

The complete ASTRA-Sim source overlay, generated-workload definitions, and
hash-checked replay-cache inputs are under
[`script/e4/backend/bundle/`](script/e4/backend/bundle/). Setup clones the
pinned ASTRA-Sim revision below `.deps/`; it does not modify `FlexEva/`.

Table 7 uses the CPU ns-3 simulator, not GPU execution. It requires `git`,
`cmake`, `protoc`, `mpicxx`, and a C++ build toolchain. Table 6 additionally
requires CUDA-enabled PyTorch, eight available physical devices for the
FakeCUDA launch, FakeCUDA, and PRoot.

## Execution

From the repository root on the evaluation server:

```bash
PYTHON_BIN=/path/to/cuda-python script/setup
script/run_e4
```

`script/run_e4` runs all three Table 6 workload cases, generates their raw
rank traces, validates the generated workload results, builds/runs all six
Table 7 backend cases, and lets the Table 7 driver verify each full/RAS pair.

Individual checks are:

```bash
python3 script/e4/validate_results.py
python3 script/e4/workload_generality/analyze_source_partitions.py
python3 script/e4/workload_generality/measure_workload_generality.py --help
python3 script/e4/backend/bundle/overlay/scripts/measure_table7_backend_generality.py self-test
```

The Table 6 raw output layout is:

```text
trace/e4/table6/<case>/{anchor,candidate}/traces/
  rank_<n>.jsonl
  rank_<n>_markers.jsonl
```

The generated CSV and JSON outputs are:

```text
result/e4/generated/table6/{summary.csv,result.json,timing_samples.csv,source_partition_analysis.{json,csv}}
result/e4/generated/table7/{gpt,moe}/{summary.csv,result.json}
```

## Checks

The paper-facing Table 6 ledger must round to initialization metrics
`0.778/0.861/0.862`, refresh speedups `3.62/4.82/4.38`, and reuse rates
`79.15/91.95/89.12%`. The paper-facing Table 7 ledger must round to the six
submitted time-avoidance percentages and speedups in
[`result/e4/table7.csv`](result/e4/table7.csv). Its percentage is the submitted
`100 * (1 - 1 / speedup)` reporting formula, not the raw partition-reuse rate.

Fresh Table 6 validation requires three successful 16-rank rows, positive
event counts, consistent selected-event reuse arithmetic, and non-empty raw
rank/marker files. Fresh Table 7 validation requires all six cases, the exact
mutation partition counts, zero-return full and RAS simulations, equal
`simulated_ns`, and active incremental RAS init/complete events for every
modeled rank. Fresh diagnostics remain in `result/e4/generated/` and do not
overwrite the submitted ledgers.
